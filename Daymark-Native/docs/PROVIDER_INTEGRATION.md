# Google and Microsoft integration boundary

Version 0.9 implements the first read-only transport stage: provider-library browser authorization, manual calendar discovery, bounded full event snapshots and an atomic SQLite cache. Actual account sign-in and live behavior still need end-to-end validation with registered OAuth apps. Two-way editing and incremental delta sync remain unimplemented. See [account setup](ACCOUNT_SETUP.md). The connected Google/Microsoft tools in Codex do not grant credentials to Daymark.

## Foundations already in the native core

- Stable local calendar and event IDs. Recurring occurrences use a series ID plus original source-clock start; a moved occurrence retains that identity. Cancellations remain explicit exception records.
- Local calendars, validated version-3 backups, atomic saves, migration originals, undo/redo and bounded recurrence expansion.
- `ICalendarProvider` separates calendar discovery, scoped change pages and conditional writes from Windows UI. It is a contract, not a working provider client.
- `SyncMerge` makes a three-way decision using the last synchronized baseline, local state and an explicit remote observation. Divergent edits and edit/delete races become conflicts rather than last-writer-wins overwrites. Missing delta entries are not deletion observations.
- `SyncPageBatch` stages every page before committing its completed cursor. A failed persistence callback retains the old checkpoint. The eventual persistence transaction must include normalized events, provider snapshots, conflict records, mappings, pending operations and the checkpoint together.
- Retry classification distinguishes rate limiting, authorization, permissions, conflicts, expired cursors and permanent errors. Existing writes require a version token and a stable operation ID survives retries.

These mechanisms have fixture tests. They have not been validated against real provider responses.

## Delivery sequence

1. **Account authorization and read-only calendar discovery.** Register desktop/public-client apps for the intended consumer and work/school account types. Use the system browser and PKCE for Google; use the supported MSAL public-client flow for Microsoft. Start with calendar read permissions. A user completes sign-in and consent; never collect account passwords in the calendar UI. Google documents the [desktop authorization flow](https://developers.google.com/identity/protocols/oauth2/native-app); Microsoft documents [interactive desktop token acquisition](https://learn.microsoft.com/en-us/entra/identity-platform/scenario-desktop-acquire-token-interactive).
2. **Read-only synchronization with explicit coverage.** Google uses a separate opaque sync token per account/calendar/query; retain deletions, complete all pages, and rebuild the remote mirror after token expiry without discarding local pending changes. Follow the [Google synchronization guide](https://developers.google.com/workspace/calendar/api/guides/sync). Microsoft Graph v1.0 calendar-view delta is scoped to a calendar and fixed UTC date range; track each range and calendar separately rather than treating a delta URL as a mailbox-wide token. Follow the [Graph calendar-view delta guide](https://learn.microsoft.com/en-us/graph/delta-query-events). Use case-sensitive IDs and request [Outlook immutable event IDs](https://learn.microsoft.com/en-us/graph/outlook-immutable-id) consistently.
3. **Provider fixture mapping and capability restrictions.** Store the provider's original payload/version separately from the editable normalized projection. Retain unknown recurrence, invitation, conferencing and attendee fields. Floating timed events need an explicit timezone before upload; do not guess one during migration or synchronization. Unsupported recurrence patterns or read-only/shared permissions must remain read-only; never flatten a series or strip unknown fields to make it fit the local editor. Google [series and instances](https://developers.google.com/workspace/calendar/api/guides/recurringevents) and Graph [recurrence patterns](https://learn.microsoft.com/en-us/graph/api/resources/recurrencepattern?view=graph-rest-1.0) need separate adapter fixtures, including cancellations, moved instances, DST and end-date/count conversion.
4. **Durable local edits and guarded writes.** Add transactional sync persistence and an outbox before enabling account edits. A local edit and its pending operation must commit together; acknowledgments update mappings/baselines atomically. A crash after a successful create but before its acknowledgment must not create a duplicate. Use provider-supported creation idempotency, conditional versions, cancellation tokens, finite retry budgets and backoff with jitter. Reconcile on concurrency failure. Calendar-to-calendar moves require an explicit provider operation plan; a local calendar ID change is not automatically a remote move.
5. **Recovery and user control.** Surface sync status, coverage, permission changes and conflicts. Disconnect stops work, clears credential material and follows an explicit cache-retention choice. Reconnect/full resync must preserve unresolved edits and tombstones. Test offline restart, duplicate pages, partial commits, revocation, throttling and sleep/resume with disposable provider calendars before calling writes reliable.

## Storage and credentials

Keep tokens and secrets out of event backups, preferences, Git, screenshots and logs. Use a protected per-user Windows credential/token cache; distinguish accounts and support revocation. Client IDs are configuration, not a means of keeping desktop secrets. Public desktop apps cannot protect an embedded client secret.

Version-3 JSON is the local calendar/export format. Before persisting real account mappings or outbox state, introduce a versioned transactional sync store and export/migration policy. Older previews must reject newer writable schemas instead of silently dropping metadata. Do not bolt independently written cursor or queue files onto the current event save path: a crash could otherwise advance one without the other.

No public webhook server is required to begin desktop account integration. Start with explicit/manual refresh and a bounded connected-account scheduler; network work, token refresh, retries and callbacks must stay off the WPF UI thread. Reminder delivery, tray lifecycle, signing and automatic updates remain separate Windows work.
